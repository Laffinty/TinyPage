# TinyPage 综合 REVIEW 与优化方案

> 审查日期：2026-09-27
> 审查范围：全部 Python 源码（约 4,100 行）、7 个 admin 模板、5 个前端静态资源、测试、CI/部署配置
> 方法：通读全部源码 + 对 8 个可疑点编写临时验证脚本实测取证

---

## 一、结论摘要

项目骨架是合理的：双服务架构、WSGI 零框架、内容纯文件存储、模块划分（config / content / generator / security / parsers / admin）方向都对。

**但它目前不是一个"能用的产品"，而是一个"能通过单元测试的代码库"。**

根本原因有三个：

1. **模块之间的调用契约没有被任何机制保护。** `admin/app.py` 用 4 个参数调用 `actions.py` 里 3 个参数的函数，12 个写操作全部抛 `TypeError`。`tests/` 里 274 行测试**只覆盖 `security.py`**，而所有 P0 缺陷都分布在 `content / generator / admin / parsers` 这四个**零覆盖**的模块里。测试全绿，后台全挂。

2. **内容存储格式（`<!-- markdown: ... -->`）本身不安全。** 原文被 `escape_html` 写进 HTML 注释，读回来时又是一次 `escape_html`，**每次 rebuild 都会多套一层转义**。这不是偶发 bug，是不可逆的数据腐蚀。

3. **README 承诺的特性有 4 个从未真正工作过**（PWA、标签图谱、HTTP Basic Auth、翻译），而文档里没有任何机制能发现这件事。

优先级分布：

| 级别 | 数量 | 含义 |
|------|------|------|
| **P0** | 5 | 功能不可用 / 数据损坏 / 安全漏洞，必须立刻修 |
| **P1** | 17 | 明显功能缺陷或承诺落空，影响可用性 |
| **P2** | 25+ | 架构债、代码质量、一致性、可维护性 |
| **P3** | 8 | 死代码、清理项 |

## 二、P0 —— 必须立即修复

### P0-1 全部后台写操作返回 500（管理后台实际不可用）

**位置**：`tinypage/admin/app.py:215-238` ↔ `tinypage/admin/actions.py`

`app.py` 的分发逻辑统一按 4 个参数调用：

```python
# app.py:216
return actions.upload_image(environ, start_response, self.cfg, post_data)
```

但 `actions.py` 的定义只有 3 个（`start_response` 是通过闭包/闭包外变量拿的，实际根本没传）：

```python
# actions.py:37
def create_article(environ: dict, cfg: Config, post_data: dict) -> list[bytes]:
```

**实测结果**（注入合法 session + CSRF 后）：

```
POST /create -> 500 Internal Server Error
POST /regen  -> 500 Internal Server Error
POST /upload -> 500 Internal Server Error
[ADMIN-ERROR] create_article() takes 3 positional arguments but 4 were given
[ADMIN-ERROR] regenerate() takes 2 positional arguments but 3 were given
[ADMIN-ERROR] upload_image() takes 3 positional arguments but 4 were given
```

**受影响范围（12/12）**：

| Action | 定义参数数 | 实际调用数 |
|--------|-----------|-----------|
| `upload_image` | 3 | 4 ❌ |
| `create_article` | 3 | 4 ❌ |
| `save_article` | 3 | 4 ❌ |
| `delete_article_action` | 3 | 4 ❌ |
| `create_page` | 3 | 4 ❌ |
| `save_page` | 3 | 4 ❌ |
| `delete_page_action` | 3 | 4 ❌ |
| `regenerate` | 2 | 3 ❌ |
| `live_preview` | 3 | 4 ❌ |
| `set_theme` | 3 | 4 ❌ |
| `ai_assist` | 3 | 4 ❌ |
| `translate_article_action` | 3 | 4 ❌ |

即：**建文章、改文章、删文章、建页面、改页面、删页面、重新生成、图片上传、主题切换、AI 助手、翻译、实时预览** —— 全部不可用。只有登录/登出（`login_handler` / `logout_handler` 签名恰好吻合）是好的。

异常被 `app.py:131` 的宽泛 `except Exception` 吞掉并返回 500，所以**用户看到的是一个没有任何解释的 500**，日志里也只有一行 `ADMIN-ERROR`。

**修复**：

1. 统一签名。建议把 `start_response` 显式化，避免闭包隐式依赖：
   ```python
   # actions.py 全部改为
   def create_article(environ, start_response, cfg, post_data) -> list[bytes]:
   ```
2. `app.py` 的 `if/elif` 分发链换成 `functools.partial` 表驱动，消除 12 处手工同步：
   ```python
   _POST_HANDLERS = {
       "upload_image": actions.upload_image,
       "create_article": actions.create_article,
       ...
   }
   handler = _POST_HANDLERS.get(route)
   if handler is None:
       return self._send_404(start_response)
   return handler(environ, start_response, self.cfg, post_data)
   ```
3. **加签名契约测试**（见 P1-15），防止同类问题复发。

### P0-2 每次 rebuild 内容被二次转义（不可逆数据腐蚀）

**位置**：`tinypage/content.py:456-475`（`get_raw_content`）+ `content.py:577-584`（`regenerate_all_articles`）

写入时把原始 markdown 做 `escape_html` 后塞进 HTML 注释：

```python
# content.py:584
f.write(f"<!-- markdown: {escape_html(raw_content)} -->\n")
```

读取时用正则取回来：

```python
# content.py:468
markdown_match = re.search(r"<!-- markdown:\s*(.*?)\s*-->", content, re.DOTALL)
if markdown_match:
    return markdown_match.group(1)      # 返回的是"已转义"的文本
```

而 `regenerate_all_articles` 的流程是：`get_raw_content()` → 处理 → `escape_html()` → 写回。**读出来的是已转义的，再转义一次再写回**。

**实测结果**：

```
original   : Cost is $5 & <10. See [link](http://a.com).
rebuild 1  : Cost is $5 &amp; &lt;10. See [link](http://a.com).
rebuild 2  : Cost is $5 &amp;amp; &amp;lt;10. ...
rebuild 3  : Cost is $5 &amp;amp;amp; &amp;amp;lt;10. ...
rebuild 4  : Cost is $5 &amp;amp;amp;amp; &amp;amp;amp;lt;10. ...
```

每轮 rebuild 长度 +8 字符，**每一次"重新生成静态页"按钮点击都会加重一次**。含 `&`、`<`、`>`、`"`、`'` 的文章（也就是几乎所有正常文章）会持续劣化。

更严重的是：正文里只要出现 `-->`（HTML 注释、或代码块里的 `-->`），`get_raw_content` 的非贪婪正则会**在第一个 `-->` 处截断**，剩余正文永久丢失。

**修复（架构级，建议一次做对）**：

内容不该塞进 HTML 注释里。改为**分离存储**：

```
pages/article/2026-01-01-x.html   ← 纯生成的产物（可随时重建，不含源）
pages/.tinypage/src/2026-01-01-x.md ← 原始 markdown（唯一真相源）
```

元数据单独放 `pages/.tinypage/meta.json`（原子写、带 schema 版本），markdown 存 `.md` 文件。

如果为了向后兼容必须保留注释格式，则至少：
- 写入时**不转义**（改为 base64 或用不可能出现的哨兵分隔符）
- 增加一次性的迁移脚本，把存量文章解码回原文
- 在 `get_raw_content` 里对返回内容做一次**幂等的反转义**（或干脆不再转义）

> 这一项工作量最大，但它是所有内容正确性的地基，建议排在 P0-1 之后立即做。

### P0-3 静态服务器目录穿越（前缀匹配漏洞）

**位置**：`tinypage/security.py:277`

```python
base = base_dir.resolve()                       # D:\Project\TinyPage\pages
target = (base / path_str).resolve()             # D:\Project\TinyPage\pages-evil\secret.txt
if not str(target).startswith(str(base)):        # "…pages-evil…" 以 "…pages" 开头 → 通过！

```

**实测结果**：

```
doc_root = D:\Project\TinyPage\pages
target   = D:\Project\TinyPage\pages-evil\secret.txt
allowed  = True
resolved = D:\Project\TinyPage\pages-evil\secret.txt
```

`startswith` 是字符串前缀比较，不是路径包含关系。`pages-evil`、`pages_backup`、`pages.old` 这些**同级兄弟目录**全部可被读取。`StaticApp` 会照常返回文件内容。

```python
if not target.is_relative_to(base):     # Python 3.9+
    logger.warning(f"[BLOCK] Path traversal: {path_str} -> {target}")
    return False, None
```

`content.py:262` / `content.py:657` 里的同类守卫也有问题：

```python
path.resolve().relative_to(article_dir.resolve())  # 返回值被丢弃
```

这行**只靠抛异常生效**，语义不清且不产出任何结果。应改为显式判断并记日志。

### P0-4 `tinypage serve` 空密码即可登录

**位置**：`tinypage/cli.py:172-238`（`serve` 命令）

`server.py:112` 的 `main()` 会调用 `ensure_admin_password(cfg)` 生成随机密码，但**用户实际用的 `tinypage serve` CLI 完全没有这一步**，`Config.validate_startup()` 也没被调用。

结果：未设 `ADMIN_PASS` 时 `cfg.admin_pass == ""`，而 `actions.py:397`：

```python
if not secrets.compare_digest(username, cfg.admin_user) or not secrets.compare_digest(password, cfg.admin_pass):
```

`secrets.compare_digest("", "")` → **True**。攻击者提交空密码即可登录管理后台。

`AuthFailureTracker` 的锁定机制也救不了：空密码**每次都验证通过**，永远不计入失败次数。

**修复**：

1. `cli.serve` 中补上 `ensure_admin_password(cfg)` + `validate_startup()` 警告输出（与 `server.main()` 对齐）。
2. 更根本的修复：把这段逻辑从 `server.py` 抽到 `config.py` 或新建 `bootstrap.py`，让**所有入口**（`cli.serve` / `server.main` / 未来任何入口）共享同一个"就绪"函数，避免两处漂移。
3. `login_handler` 增加 `if not cfg.admin_pass: return error_response(start_response, "503 Service Unavailable", ...)` 兜底。

### P0-5 Markdown 透传原始 HTML → 存储型 XSS

**位置**：`tinypage/parsers/markdown.py:57-63`

```python
def render_markdown(text: str) -> str:
    if _HAS_MISTUNE and mistune is not None:
        return mistune.html(text)     # 默认 escape=False，原始 HTML 直接透传
```

**实测结果**：

```
input  = '<img src=x onerror=alert(1)>'
output = <img src=x onerror=alert(1)>
```

攻击链：

1. 内容作者（或 AI 返回内容、或被翻译的外部文本）写入 `<img src=x onerror=...>`
2. `live_preview`（`actions.py:285`）把 `render_markdown()` 的结果原样返回
3. `article_form.html:34` 的 `hx-target="#live-preview"` 把它作为 **innerHTML 注入管理后台 DOM**
4. 管理后台域名的同源上下文执行脚本，持有 session cookie

管理后台的 CSP 是 `script-src 'self' 'unsafe-inline'`，**无法阻止**（`'unsafe-inline'` 就是允许内联脚本）。

**修复**：

1. `mistune.html(text, escape=True)`（mistune 3.x），或改用 `mistune.create_markdown(escape=True, plugins=[...])` 白名单插件。
2. 若确实需要允许作者写内联 HTML，改为显式白名单：只允许 `<b> <i> <em> <strong> <code> <pre> <br> <hr> <sub> <sup> <mark> <figure> <img> <table>`，且 `<img>` 强制 `src` 走 `validate_url_protocol` + 剥除所有 `on*` 属性。
3. `live_preview` 额外加一层：用 `DOMPurify`（前端）或 `bleach`（后端）净化。
4. CSP 去掉 `'unsafe-inline'`，改用 nonce（`admin/responses.py` 已经能拿到 `start_response`，加 nonce 成本很低）。

## 三、P1 —— 影响可用性的功能缺陷

### P1-1 页面标题 / 描述二次转义

**位置**：`tinypage/generator.py:97,183-185` ↔ `tinypage/core/template.py:112-125`

`generator.py` 先转义一次，再把结果传给 `render_skeleton`，后者**又转义一次**：

```python
# generator.py:97
site_title = escape_html(cfg.site_title)
# template.py:113
site_title=escape_html(site_title),      # 又来一遍
```

**实测**：

```
<title>          = 首页 - Tom &amp;amp; Jerry
post summary     = R&amp;D
article title    = A &amp; B &lt;x&gt;
```

页面上显示 `Tom &amp; Jerry`（字面量），搜索结果、OG 卡片、浏览器标题全部受影响。

**修复**：确立**单一转义责任**原则 —— `render_skeleton` 负责转义，所有调用方传**原始值**。或反过来：调用方转义，`render_skeleton` 不再转义。推荐前者（模板层统一兜底，新增调用点不会漏）。同时删掉 `render_admin_page` 里 `title=escape_html(title)` 的重复转义。

### P1-2 目录锚点 id 重复，ToC 链接失效

**位置**：`tinypage/parsers/toc.py:138-140`

```python
for text, heading_id in heading_map.items():
    if text in content:                              # 子串匹配！
        return f"<{tag} id=\"{heading_id}\"{attrs}>{content}</{tag}>"
```

`"Intro"` 是 `"Introduction to the project"` 的子串，先匹配到的就返回。

**实测**：

```
headings = [('Intro','intro'), ('Introduction to the project','introduction-to-the-project')]
rendered = <h2 id="intro">Introduction to the project</h2><h2 id="intro">Intro</h2>
```

两个标题拿到**同一个 id**（HTML 非法），目录点击永远跳到第一个。

**修复**：改为按渲染顺序**一一对应**消费，而不是子串搜索：

```python
def add_heading_ids(html_content, headings):
    it = iter(headings)
    def repl(m):
        tag, attrs, content = m.group(1), m.group(2), m.group(3)
        if "id=" in attrs:
            return m.group(0)
        try:
            h = next(it)
        except StopIteration:
            return m.group(0)
        return f'<{tag} id="{h.id}"{attrs}>{content}</{tag}>'
    return re.sub(r"<(h[1-6])([^>]*)>(.+?)</\1>", repl, html_content, flags=re.DOTALL)
```

顺带删除同文件 `toc.py:111-117` 的死函数 `replace_heading`（定义了从未被调用）。

### P1-3 标题含下划线 → 文章无法创建

**位置**：`tinypage/security.py:22` ↔ `security.py:365` ↔ `security.py:365`

两个正则的字符集**不一致**：

```python
# security.py:22  文件名校验
SAFE_FILENAME_PATTERN = re.compile(r"^\d{4}-\d{2}-\d{2}-[a-zA-Z0-9\u4e00-\u9fa5-]+\.html$")

# security.py:365  slug 生成（\w 包含下划线）
slug = re.sub(r"[^\w\u4e00-\u9fa5-]", "-", text.lower()).strip("-")
```

**实测**：

```
title='Hello_World'  slug='hello_world'  valid_filename=False
```

`actions.create_article` 拼出 `2026-01-01-hello_world.html` → `write_article` 抛 `ValueError: Invalid filename` → 用户看到 500。同理 `actions.py:54` 的重名兜底 `secrets.token_urlsafe(4)` 也可能产生 `_`。

**修复**：把字符集提取为**单一常量**，两处共用：

```python
_SLUG_CHARS = r"a-zA-Z0-9_\u4e00-\u9fa5"          # 或决定去掉 _
SAFE_FILENAME_PATTERN = re.compile(rf"^\d{{4}}-\d{{2}}-\d{{2}}-[{_SLUG_CHARS}-]+\.html$")
def slugify(text, ...):
    slug = re.sub(rf"[^{_SLUG_CHARS}-]", "-", text.lower())
```

并加一条不变式测试：*"任何 `slugify()` 的输出都必须能通过 `validate_filename()`"*。

### P1-5 `parse_meta` 读不到 `markdown` 字段

**位置**：`tinypage/content.py:86`

```python
for i, line in enumerate(f):
    if i >= 7:          # 只读前 7 行（索引 0..6）
```

### P1-6 `save_page` 改名会丢数据

**位置**：`tinypage/admin/actions.py:157-163`

```python
new_fname = f"{slug}.html"
if new_fname != fname:
    old_path = cfg.standalone_dir / fname
    if old_path.is_file():
        delete_standalone(old_path)      # 先删
```

**修复**：先校验、先写新文件、确认成功后再删旧文件（`os.replace` 天然支持原子替换，同目录内改名直接用 `Path.rename` 即可）：

```python
new_path = cfg.standalone_dir / new_fname
if not validate_page_filename(new_fname):
    return error_response(start_response, "400 Bad Request", "Invalid slug")
write_standalone(cfg.standalone_dir, new_fname, title, content)
if new_path != cfg.standalone_dir / fname:
    delete_standalone(cfg.standalone_dir / fname)
```

### P1-9 改标题导致 slug 与文件名脱钩

**位置**：`tinypage/admin/actions.py:84-88`

```python

write_article(cfg.article_dir, fname, title, date, s, ...)   # 但 fname 还是旧文件名
```

`ArticleMeta.url` 是 `f"/article/{self.file}"`（用文件名），但 `slug` 字段被改成了新值。于是：

- 站内链接用文件名 → 仍可用
- 但 `build_article_title_map` 用 `article.slug or slugify_for_link(article.title)`（`bidirectional_links.py:120`），`[[wikilink]]` 解析和 sitemap 用的是 slug → **不一致**
- 改名后新旧 slug 混存，双向链接解析结果不可预测

**修复**：明确策略并在 UI 上体现 —— 要么改标题时同步重命名文件（并保留旧名到新名的重定向页），要么**不改 slug**（slug 只在创建时确定一次，改标题不影响）。

推荐后者：slug 作为不可变标识，改标题只改 `title`。改动小、无破坏性。

### P1-10 PWA 完全不工作（`sw.js` 从未被注册）


- `CACHE_NAME = 'tinypage-v1'` **硬编码不变** → 用户永远拿不到更新。改为由构建时注入内容哈希。

### P2-1 配置系统形同虚设

### P2-3 `waitress` 硬依赖，"零依赖"承诺不成立

**位置**：`tinypage/server.py:83,93`、`tinypage/cli.py:210,216`

### P2-4 `build_backlink_index` 是 O(n³)，且缓存失效逻辑脆弱

应该先建 `{lower_title: article}` 和 `{slug: article}` 两张字典，降到 O(n·k)。

## 七、关于"AI 能力有限导致的不完善"——根因与对策

这次扫描暴露的根因不在于"当时 AI 写代码水平低"，而在于**缺少反馈闭环**：

1. **没有一条端到端的冒烟测试**。一个"登录 → 建文章 → 看到文章出现在首页"的脚本测试，能在 5 秒内发现 P0-1。
2. **没有类型检查 / lint**。`actions.fn(environ, start_response, cfg, post_data)` 调用 3 参函数这种错误，`mypy` 一轮就抓出来。`pyproject.toml` 里连 `[tool.mypy]` 都没有。
3. **契约靠记忆而非机器**。12 个 action 手写 `if/elif` 分发，没有任何工具保证签名一致。
4. **README 是手写的，不是从代码生成的**。于是 4 个特性"宣称存在但从未工作"长达数个版本。

**最小可行对策**（建议随第一批一起落地）：

```
.github/workflows/ci.yml
  ├── ruff check + ruff format --check
  ├── mypy --strict tinypage/
  ├── pytest（含新增的 5 个测试文件）
  └── pytest tests/smoke/test_e2e.py   # 建文章 → 首页可见 → 删文章
```

配套加 `pyproject.toml` 配置：

```toml
[tool.ruff]
line-length = 100
[tool.ruff.lint]
select = ["E", "F", "I", "B", "UP", "S"]   # S = bandit 安全规则
[tool.mypy]
python_version = "3.10"
strict = true
```

`mypy --strict` + `ruff` 的 `S` 规则（bandit）会直接抓出 P0-3（路径穿越）、P0-5（XSS）、P0-4（硬编码凭据比较）这一类问题。**这是投入产出比最高的一项。**
